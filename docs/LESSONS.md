- **FLF2V (first/last frame)** par segment : `LTXVPreprocess(img_compression 35)` ×2 → `LTXVAddGuide(frame_idx 0, strength 0.7)` → `LTXVAddGuide(frame_idx -1, 0.7)` → sampler sur le latent AddGuide2[2] → **sortie sampler slot 1 (`denoised_output`)** → `LTXVCropGuides` (conditioning depuis AddGuide2) → `VAEDecodeTiled(768/64/4096/64)`.
- **Piège n°3 — recadrage sauvage** : `LTXVAddGuide` center-croppe/zoome toute image guide dont le ratio ≠ latent → résultat "sans rapport" avec l'image. Toujours insérer `ImageScale(lanczos, width, height, crop:"center")` avant `LTXVPreprocess`, et dériver le format vidéo de la 1ʳᵉ image (côté long ≤1280, multiples de 32).
- **Piège n°4 — prompt de mouvement** : en FLF2V le texte doit décrire le MOUVEMENT ; un prompt de contenu (ex. prompt de poster) fait dériver le milieu des segments vers ce contenu (effet "diaporama d'images inventées"). Segments courts (2–3 s) = fidélité ; longs (5 s+) = dérive.
- Frames valides : `8n+1` (ex. 49 ≈ 2 s @ 25 fps ; formule `8*round((s*25-1)/8)+1`).
- La hauteur/largeur est arrondie au multiple de 32 inférieur au rendu (720 → 704) : normal.
- **Audio** : AUCUN modèle supplémentaire requis — `LTXVAudioVAELoader(ckpt_name="ltx-2.3-22b-distilled-1.1.safetensors")` charge l'audio VAE depuis le checkpoint (le "vocoder" listé par certains templates n'est pas nécessaire au chemin standard). Câblage : `LTXVEmptyLatentAudio(frames, 25, 1, audio_vae)` → `LTXVConcatAVLatent(video_latent, audio_latent)` AVANT le sampler → `LTXVSeparateAVLatent(sampler[1])` → slot 0 = vidéo (vers CropGuides/decode), slot 1 → `LTXVAudioVAEDecode` → `CreateVideo.audio` (entrée optionnelle). Multi-segments : chaîner les AUDIO avec `AudioConcat(direction:"after")`.

## API & graphes ComfyUI

- **Piège n°5 — slots `ComfyMathExpression`** : slot 0 = FLOAT, slot 1 = INT. Une entrée INT (ex. `length`) câblée sur le slot 0 → `return_type_mismatch`.
- **Piège n°6 — ids non numériques** : certains templates API contiennent des clés comme `"PH"`. Pour générer de nouveaux ids : `Math.max(0, ...keys.map(Number).filter(Number.isFinite)) + 1`.
- `ImageStitch(match_image_size:true)` étire l'image la plus petite : équilibrer les lignes d'une grille (4 → 2+2, 5 → 3+2) sinon une ligne courte devient géante.
- Format UI : links du graphe principal = tableaux `[id,src,slot,dst,slot,type]` ; dans `definitions.subgraphs` = dicts (`origin_id`/`target_id`) et les ids **-10/-20** sont les nœuds frontière entrée/sortie (pas des liens cassés). Types "virtuels" absents d'object_info mais valides : `MarkdownNote`, `Note`, `Reroute`.
- Ordre des `widgets_values` (format UI) : inputs widget du schéma dans l'ordre required+optional ; tout INT avec `control_after_generate:true` est suivi d'un widget parasite ("randomize"/"fixed") à ignorer. COMBO en deux styles (liste littérale vs `type:"COMBO"`+`extra.options`). Géré par `tools/convert.py`.
- Templates officiels de référence : dans le conteneur `comfyui-nvidia` sous `/comfy/mnt/venv/lib/python3.12/site-packages/comfyui_workflow_templates_media_{image,video,other}/templates/`. **Toujours partir d'eux** pour un nouveau modèle, jamais de mémoire.

- **Piège n°9 (CRITIQUE) — les cuts LTX i2v dérivent fréquemment vers un contenu SANS RAPPORT avec la keyframe/le personnage** : testé en rendu réel sur les DEUX runs de qualification (N=8 du 2026-07-17, frames extraites au milieu de chaque cut, pas seulement à la première/dernière image) — sur 9 cuts (8 plans + tenue), seuls 3 gardent clairement le personnage et le décor (cuts 4, 5, 9), 2 sont ambigus/partiels (cuts 2, 6 — un intrus au premier plan pour le 6), et **4 dérivent totalement** vers un contenu générique sans rapport (cut 1 → fontaine ornementale, cut 3 → homme en costume dans une rue, cut 7 → homme agenouillé près d'une fontaine, cut 8 → champ de blé). Sur le run N=4 angles, les 4 cuts dérivent presque tous (ex. une pomme sur fond blanc, un mur de roses) — voir frames dans le rapport de qualification LOT 3. **Cause probable** : `submitCutJob` passe **uniquement** `shot.motion` (ex. "Slow crane rise upwards revealing scale") comme prompt — une phrase de mouvement de caméra courte, sans aucun mot de scène/personnage. Le template `api/ltx_i2v.json` (`enrich:"builtin"`) route ce texte dans l'enhancer natif LTX (`TextGenerateLTX2Prompt`, node texte **sans aucune entrée image** — confirmé en lisant le graphe : il ne reçoit que `clip`+`prompt`) qui élabore alors une scène complète **à partir de rien**, sans connaître le contenu de l'image de référence. Comme le pipeline distillé tourne à **cfg 1** (piège n°5 déjà documenté : l'adhérence dépend entièrement de ce texte enrichi), quand l'enhancer invente une scène sans rapport, le rendu suit cette scène inventée plutôt que l'image-guide — qui n'ancre fiablement que la toute première frame. Ce piège est différent (et plus grave) du problème d'angle Qwen-Edit ci-dessous : il touche la vidéo, pas la keyframe, et affecte la promesse même de l'"animatic" (montrer le mouvement de LA scène décrite). **CORRIGÉ (2026-07-17)** : `submitCutJob` ne passe plus `shot.motion` seul mais un prompt qui ancre l'enhancer sur le contenu réel de la keyframe — scène du plan + fiche personnage + mouvement de caméra : `` `${scene}. ${charDesc}. Camera motion: ${motion}.` ``. La fonction reçoit désormais `scene` et `charDesc` en paramètres ; ses DEUX appelants ont été adaptés (mode Auto `generateStoryboardV2` : `charDesc` local + `scenes = shots.map(s => s.scene)` ; mode Réalisateur `directorStep3` : `charDesc` destructuré de l'état `director` + même map de scènes). La leçon générale : à cfg 1, tout node texte enrichi sans entrée image doit recevoir une description de la scène cible, pas seulement une consigne de mouvement — sinon il invente. Voir aussi piège n°4 (prompt de contenu vs mouvement en FLF2V), même racine. **ÉVOLUTION (ancrage double, même jour, plus tard dans la journée)** : depuis l'ajout d'une fiche décor structurée gemma (`locationSheetFromBrief` → `locDesc`), `submitCutJob` ancre le prompt du cut sur scène + personnage + **décor** : `` `${scene}. ${charDesc}. ${locDesc}. ## Canvas / litegraph — 2026-09-08

- **Piège n°17 — un combo litegraph construit avec un tableau déjà résolu (`.map(...)` figé) ne voit jamais une liste peuplée après coup par un fetch réseau.** En retirant la curation manuelle des LoRA (`KREA2_LORAS`/`H3_STYLE_LORAS` de `js/engine.js`, désormais peuplées de façon asynchrone par `fetchLoraOptions()` au chargement du module), les combos "style (LoRA)" de `js/nodes-simple.js`/`js/nodes-advanced.js` sont restés bloqués sur la liste vide initiale (`["", "Aucun"]`) même une fois le fetch résolu — le nœud litegraph avait déjà capturé `{ values: E.KREA2_LORAS.map(l => l[0]) }` au moment de sa construction (`addWidget("combo", …)`), et cette copie ne se met jamais à jour même si le tableau source, lui, est ensuite muté (`push`). Cause trouvée en lisant le code source de `litegraph.js` lui-même (pas dans sa doc) : le cas `"combo"` du handler `pointerdown` du widget relit `widget.options.values` **au moment du clic**, et si cette propriété est déjà une **fonction**, il l'appelle à cet instant plutôt que d'utiliser une valeur figée — mais si c'est un tableau, il l'utilise tel quel, sans jamais le relire ailleurs. **Correction : passer une fonction (`values: () => E.KREA2_LORAS.map(l => l[0])`, ou une référence de fonction nommée type `loraIds`/`h3LoraIds`) plutôt qu'un tableau pré-calculé**, dès qu'un combo doit refléter une source qui peut changer après la construction du nœud. Ce mécanisme est spécifique aux combos litegraph (Canvas) — un `<select>` DOM classique (Studio, `index.html`) n'a pas cette relecture automatique et doit être repeuplé explicitement par un rendu appelé quand la source change (`renderLoraSelect()`).

## Mode Réalisateur partagé `storyboard_v2` / `reference2video` — 2026-09-08

- **Piège n°18 — un garde `director?.pipeline === X` doit être choisi pour le résultat qu'il produit quand `director` est `null`, pas pour sa symétrie apparente avec l'autre branche.** En portant la coquille studio (`STUDIO_SECTIONS`, `updateGateState()`) sur un 2ᵉ pipeline (`reference2video`, en plus de `storyboard_v2`), `updateGateState()` a dû décider quel onglet/bouton activer selon `director.pipeline`. `resetDirectorZone()` (appelée entre autres à chaque changement de pipeline via `updateModelOptions()`) positionne `director = null` **avant** d'appeler `updateGateState()` — donc `updateGateState()` s'exécute régulièrement avec `director` à `null`, pas seulement en session active. Le test retenu est `director?.pipeline === "reference2video"` : avec `director` null, `undefined !== "reference2video"` → branche `else` = forme `storyboard_v2` (onglets Storyboard/Montage re-verrouillés, onglet Vidéo caché) — exactement le comportement d'avant l'introduction du 2ᵉ pipeline. Un test à première vue plus « symétrique », `director?.pipeline === "storyboard_v2"`, aurait donné le résultat **inverse** au même instant : `director` null → `undefined !== "storyboard_v2"` → bascule dans la branche `reference2video`, qui masque Storyboard/Montage et affiche l'onglet Vidéo verrouillé alors qu'aucune session r2v n'est active — état d'onglets faux juste après un reset ou un changement de pipeline vers `storyboard_v2` (le pipeline par défaut de l'app). Repéré en traçant l'ordre d'appel `resetDirectorZone()`→`director=null`→`updateGateState()`, pas en le constatant à l'usage. Leçon générale : quand une branche `?.`-safe doit avoir un comportement par défaut pour l'état « absent », choisir explicitement la branche dont le résultat par défaut colle au comportement historique/attendu — la formulation la plus symétrique en apparence n'est pas nécessairement celle qui donne le bon défaut.

- **Piège n°20 — reproduire la grille 17n+5 en JavaScript demande un modulo à la Python** : l'expression des templates H3 est `max(5, round(a*24)) + (5 - (max(5, round(a*24)) % 17)) % 17`, et son `%` rend un résultat **positif** sur une valeur négative. Transcrite naïvement, la formule donne **22 frames** pour une demande de 1 s au lieu des 39 mesurées en rendu réel (piège n°11) — un écart silencieux de 40 %. `h3VideoFrames` corrige par `((x % 17) + 17) % 17`. - **Piège n°23 — un texte de rôle écrit pour un seul sujet devient contradictoire dès qu'il y en a deux (2026-09-22).** `H3_SUBJECT_KINDS.character.lead` valait « is the main character in », formulation juste tant qu'un clip r2v ne portait qu'un personnage. Quand les cuts H3 ont réutilisé cette table (PR #3) sur un plan de storyboard, qui en accepte deux, `subject_definitions` a commencé à déclarer **deux** « main character » : deux revendications exclusives pour le même clip, que rien ne signale — pas d'erreur, pas de job en échec, juste un modèle à qui l'on demande de choisir. Le même passage oubliait le second sujet dans la phrase d'ancrage du corps narratif (`… is in <Subject N>`), qui n'en plaçait qu'un dans le décor. **Leçon : une constante de vocabulaire porte une hypothèse de cardinalité qui n'est écrite nulle part.** Avant de réutiliser une table de formulations dans un second contexte, vérifier combien d'entrées de chaque type ce contexte peut produire. La parade ici tient en une variante (`leadMulti`, « is a character in ») retenue dès que le plan porte plus d'un personnage — le chemin à un seul sujet, le seul qualifié en rendu, reste inchangé au caractère près (vérifié par comparaison des prompts compilés avant/après).

- **Piège n°24 — la variante rangeait la DESCRIPTION du sujet là où l'app attend le PROMPT envoyé (2026-09-22).** Première session de test sur GB10 : « les character sheets proposent des vues identiques du personnage, aucun intérêt », capture à l'appui d'une planche montrant cinq fois la même pose au lieu d'un turnaround. Le graphe et le gabarit n'étaient pourtant pas en cause. `directorStep1` (et son jumeau `directorStepR2V1`) rangeait sur la variante de planche `prompt: charDescFromFields(charFields)` — la description compilée des champs, pas le prompt réellement soumis, qui est `compileCharsheetPrompt(...)`, soit cette description **enrobée du gabarit** (turnaround, colonne d'expressions, bandeau de palette, `SHEET_CLEAN`). Tant qu'on ne touche à rien, invisible : le premier rendu part du bon prompt. Mais « ✎ Prompt » rouvre `variant.prompt`, donc la description nue ; l'utilisateur l'enrichit, applique, et `regenerateSheet` envoie ce texte **verbatim** (c'est la règle du projet) — le gabarit a disparu du prompt sans que rien ne le dise, et Krea 2 rend un sujet répété en cinq exemplaires au lieu d'une planche. Même mécanique sur la planche décor. **Corrigé** : le prompt est compilé une seule fois au point de soumission, passé au graphe ET rangé sur la variante, donc `variant.prompt` est par construction ce qui est parti dans le graphe. **Leçon générale, valable partout où l'app garde une trace d'un job** : quand un champ sert à la fois de mémoire et de point de reprise pour l'utilisateur, il doit contenir l'artefact ENVOYÉ, jamais une de ses entrées — sinon l'écart ne se voit qu'après un aller-retour dans l'UI, et il se voit sous la forme d'un rendu « plausible mais faux », exactement le cas d'aveuglement du piège n°14. Corollaire appliqué au même endroit : une keyframe jamais éditée à la main **recompile** son prompt à la régénération (sinon éditer l'action d'un plan ou y tagger un second sujet ne changeait rien) ; une keyframe dont le prompt a été édité n'est jamais recompilée par-dessus. Les deux moitiés de la règle « prompt éditable, prompt verbatim » vivent dans ce `if`.

- **Piège n°25 — faire décrire par le LLM un sujet que le brief ne contient pas (2026-09-22).** « + Ajouter un sujet » demandait à gemma le sujet suivant du brief, puis lançait sa planche aussitôt. Sur un brief à un seul sujet — le cas courant — gemma n'a rien à trouver : il **invente**, et son défaut est un être humain (d'où un panda roux devenu Superman sur la planche du sujet 2). Une génération non demandée partait donc en rendu sur du contenu inventé. Le bouton pose désormais un emplacement **vide** : pas d'appel gemma, pas de job, l'utilisateur décrit le sujet (champs ou « ✎ Prompt ») puis lance « Générer la planche ». Ce que ça coûte : rien d'automatique n'aide plus quand le brief décrit vraiment deux sujets. Ce que ça évite : un rendu inventé, non demandé, et un `kind` faux pour toute la session. **Leçon : ne pas demander à un LLM de combler une absence dans l'entrée utilisateur ; il ne répond jamais « il n'y en a pas ».**

- **Piège n°26 — un jeton de balisage donné à gemma revient abîmé, et le prompt reste « valide » (2026-09-22).** Le Prompt Relay en moteur Minimax H3 laisse l'utilisateur désigner les sujets par le jeton de la grammaire H3, `<Subject 1>`. Le bouton « ✨ Enrichir » envoyait le texte du segment **tel quel** à gemma, avec pour seule protection une consigne lui interdisant d'écrire des jetons. Constaté sur un run réel de six segments : gemma les recopie quand même, et il les abîme — `>Subject 1>` (chevron ouvrant devenu fermant) sur un segment, `<Subject 1> 's fingers` (espace avant l'apostrophe) sur un autre, plus un `,.` de recopie. Rien ne le signale : le job passe, le clip sort, et c'est aux pixels qu'on découvre qu'un sujet n'a pas été reconnu (piège n°14). C'est la **troisième** fois que la même parade s'impose (pièges n°16 et n°21) : une consigne ne protège pas un texte, seul le code le protège. `h3TokensOut` remplace chaque jeton par un **mot nu** (`SUBJECTREF1`) avant l'appel — un modèle de langue traite un mot nu comme un nom propre et le recopie intact, là où `<Subject 1>` ressemble à du balisage qu'il croit devoir reformater — et `h3TokensIn` le remet après. `h3NormalizeTokens` ferme la marche en réparant un jeton mal reformé et les deux scories observées ; il ne s'applique **qu'à la sortie de gemma**, jamais au texte de l'utilisateur, qui part verbatim (règle du projet). **Leçon : un jeton de balisage n'est pas du texte à enrichir. Il ne se demande pas, il ne s'interdit pas, il se retire.** Corollaire : c'est aussi le validateur du composer de référence `BMB12d3/minimax-h3-prompt-composer` (labels non canoniques, nom propre à la place du label), noté « à prendre un jour » depuis le 2026-09-21 et pris ici.

- **Piège n°27 — `ImageFromBatch` à index négatif vise une tranche vide dans l'implémentation de référence (2026-09-22).** Le piège n°22 note que `batch_index: -1` est accepté par l'API là où le widget annonce un minimum de 0, et la chaîne relay tourne effectivement avec. Mais le nœud calcule `batch_index = min(taille - 1, batch_index)` puis tranche `images[i : i + length]` : à `i = -1, length = 1` la tranche est `images[-1:0]`, donc **vide**. Le comportement ne dépend donc pas de nous, il dépend de la version installée. Un index **positif surestimé**, lui, est garanti par la ligne de bornage : `min(taille - 1, 999)` retombe toujours sur la dernière frame, quelle que soit la version. Le nombre de frames est d'ailleurs connu d'avance côté JS — les deux moteurs tournent à 24 fps, H3 sur la grille 17n+5 (`h3VideoFrames`) et LTX 2.5 sur 8n+1 (`ltx25Frames`) — donc viser la n-ième frame avant la fin ne demande aucune lecture de la vidéo. C'est ce que fait `buildTransitionStripGraph`, qui extrait cinq candidates (la dernière frame et les quatre qui la précèdent, par pas de 3 frames) pour que l'utilisateur choisisse l'image de transition. **Leçon : ne pas bâtir sur un comportement d'index négatif quand la même intention s'écrit avec un index positif que le code du nœud borne lui-même.**

- **Piège n°28 — une image de référence qui n'alimente que le conditioning ne suffit pas : le décor doit être nommé EN MOTS (2026-09-22).** `compileKeyframePrompt` désignait le décor uniquement par « use the second reference image only as the guide for the environment ». - **Piège n°29 — le « strip-then-reappend » vaut aussi pour les planches, pas seulement pour les keyframes (2026-09-22).** `enrichSheetText` envoyait le prompt de planche ENTIER à gemma sous `KREA2_ENRICH_SYSTEM`, la consigne d'**image unique** (sujet→style→lumière→optique→composition, 40–100 mots). gemma faisait donc exactement ce qu'on lui demandait : il rendait une belle photo de scène, et la composition multi-vues (turnaround, colonne d'expressions, bandeau de palette, `SHEET_CLEAN`) disparaissait avec. Un sujet ajouté à la main puis décrit dans la modale ✎ Prompt ne rendait plus jamais de planche, seulement une photo — c'est le point n°2 du run GB10 du 2026-09-22. Correctif : `sheetSkeleton`/`stripSheetSkeleton`/`wrapSheetDesc` amputent le prompt de son squelette avant l'appel et le remettent après, et gemma reçoit une consigne dédiée (`SHEET_DESC_ENRICH_SYSTEM`) qui ne décrit que ce que le sujet **est** — ni fond, ni scène, ni cadrage, ni lumière, tout cela étant déjà posé par le gabarit. Le repli va toujours dans le sens de la planche : si le squelette n'est pas reconnu (prompt réécrit de zéro), le texte entier est pris pour la description et re-enveloppé. **Leçon : une consigne d'enrichissement est spécifique à ce qu'on enrichit — un prompt d'image et une fiche d'identité de sujet ne se rédigent pas avec la même.**

- **Piège n°30 — un sujet décrit seulement dans la modale ✎ Prompt part sans identité dans les keyframes et les cuts (2026-09-22).** « + Ajouter un sujet » pose un emplacement vide (décision du 2026-09-22) et l'utilisateur peut le décrire de deux façons : les champs du menu Personnage, ou la modale ✎ Prompt. Un sujet décrit par la modale avait donc une planche correcte et une **identité vide** partout en aval : « the appearance guide for one single other character, , and use the third reference image… ». `regenerateSheet` reverse désormais la description du prompt dans le premier champ quand il n'y en a aucune. Le prompt, lui, n'est pas touché : il part verbatim, la règle projet tient. **Leçon : quand deux chemins d'entrée décrivent la même chose, vérifier que les deux remplissent la structure que le reste du code lit.**

- **Piège n°31 — « prompt verbatim » ne dispense pas de remettre l'ancrage (2026-09-22).** Sur le plan 4 du run GB10, l'utilisateur a ouvert `✎ Prompt` d'une keyframe, effacé le prompt compilé et tapé sa phrase d'action française à la place. Le texte est parti verbatim, comme la règle projet l'exige — mais sans les phrases de rôle des images de référence et sans le bloc d'ancrage. Qwen-Edit s'est alors contenté de recomposer les planches qu'on lui donnait : la keyframe rendue est un **collage** de la planche produit, de ses vignettes et du bandeau de palette. Le symptôme ressemble au piège n°17 (planche annotée) mais la cause est tout autre, et rien dans l'UI ne signalait que le prompt était amputé.
