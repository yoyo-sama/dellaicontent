# Architecture

## Vue d'ensemble

```
Navigateur ── index.html (nginx :8090, statique)
   │  fetch/WS
   ├── ComfyUI :8188      REST /prompt /history /queue /view /upload/image /object_info /models/*
   │                      WS /ws?clientId=…  (progress, executed, execution_success/error)
   ├── Ollama :11434      /api/chat (gemma4:e4b : enrichissement + découpage en plans)
   └── APIs cloud (opt.)  OpenAI gpt-image-1, Gemini gemini-2.5-flash-image (clé en sessionStorage)
```

Tout est côté client. Les graphes ComfyUI sont soit des **templates API substitués**, soit **construits dynamiquement en JS**, puis POSTés à `/prompt`. Le suivi se fait par WebSocket (jobs, assets) avec relecture d'`/history` en fin de job (`collectHistory`) pour les sorties que le WS ne remonte pas et pour l'extraction des prompts.

## Formats de workflows

**Format UI** (`workflows/*.json`) : graphes complets exportés ComfyUI (`nodes`/`links`/`widgets_values`, éventuellement `definitions.subgraphs`). Usage : drag-drop dans l'interface ComfyUI. Non consommables par `/prompt` directement → `tools/convert.py` les convertit en API.

**Format API** (`workflows/api/*.json` et builders JS) : `{ "<id>": { "class_type", "inputs": { nom: valeur | [refId, slot] } } }`. Les templates de `api/` contiennent des placeholders substitués textuellement par `buildGraph()` :

| Placeholder | Remplacé par |
|---|---|
| `"{{PROMPT}}"`, `"{{NEGATIVE_PROMPT}}"`, `"{{IMAGE}}"`, `"{{IMAGE2}}"` | chaînes JSON |
| `"{{SEED}}"`, `"{{WIDTH}}"`, `"{{HEIGHT}}"`, `"{{BATCH}}"` | nombres |
| `"{{DURATION}}"` (s), `"{{FRAMES}}"` (= durée×fps+1, fps=25 par défaut) | nombres |

**manifest.json** (v2, deux sections) :
- `pipelines:[{id, label, scenario?, controls, defaults?, fps?}]` — pilote l'UI. `scenario` (chaîne ou liste) restreint le pipeline à un/des scénario(s) ; absent = disponible partout. `controls` = liste des champs de formulaire à afficher, parmi `duration, shots, hold, variants, ratio, audio, image, markets, seq, mode, mp, turboSteps, lora, refs, skipSheets` (mappés aux wraps par `CONTROL_WRAPS` — `mode` → `modeWrap` le sélecteur Auto/Réalisateur, `mp` → `mpWrap` le sélecteur mégapixels, `turboSteps` → `turboStepsWrap` le sélecteur de steps LoRA turbo Minimax H3, `lora` → `loraStyleWrap` le sélecteur de LoRA de style, `refs` → `refExtrasWrap` les champs de références supplémentaires du `reference2video`, `skipSheets` → `skipSheetsWrap` la case "Ignorer les fiches" du `reference2video`, voir section dédiée plus bas). `defaults.duration` = valeur remise au changement de pipeline. `fps` propagé à `buildGraph` pour `{{FRAMES}}` (ex. Wan = 16). Un fallback JS (`PIPELINES_FALLBACK`) couvre les 8 pipelines de base si la section manque (y compris `storyboard_v2` et `reference2video`, à l'identique du manifest).
- `workflows:[{id, label, pipeline, model, file, enrich?, builder?, fps?, anchor?}]`. `file:null` + `builder` = graphe construit en JS (dispatch via le registre `BUILDERS`). `enrich:"builtin"` (templates LTX 2.5 t2v/i2v) court-circuite l'auto-enrichissement gemma. `anchor` (`storyboard_v2` uniquement) = chemin du template API **dual** (2 images d'entrée) utilisé pour chaque keyframe (`api/qwen_edit_dual.json`, Qwen-Image-Edit 2509 + LoRA Lightning) — changer de modèle d'ancrage = changer cette seule ligne du manifest. L'ancien template mono-image (`api/qwen_edit_i2i.json`, 1 seule image d'entrée) reste sur disque, non référencé : bascule arrière = remettre son chemin sur cette ligne.

**Nav par profils métiers** (`const PROFILES`, au-dessus de la logique scénario) : couche de présentation pure — une carte de profil (Réalisateur, DA/Motion designer, Social/Marketing, Monteur) ne fait que cliquer l'onglet scénario correspondant puis présélectionner un pipeline, sans état de génération propre ni court-circuit du routing `activeScenario`/`SCENARIOS`/`refreshPipelineOptions`.

## Flux Generate (handler du bouton)

1. Auto-enrichissement gemma optionnel (sauf `enrich:"builtin"`).
2. Calcul seed/ratio/batch/durée.
3. Si `wf.builder` : dispatch via le registre `BUILDERS` (`flf2v`→`generateSequence`, `storyboard_v2`→ selon `directorMode` : `generateStoryboardV2` (mode Auto, chaîne complète) ou `directorStep1` (mode Réalisateur, ne lance que l'étape 1 — la suite est pilotée par les boutons de `directorZone`), `campaign_full`→`generateCampaignFull`, `reference2video`→ **d'abord** la case `#skipSheetsToggle` (bypass fiches, prioritaire sur le mode : rien à revoir si rien n'est auto-généré) : cochée ⇒ toujours `generateReference2Video` (qui gère le bypass en interne), quel que soit `directorMode` ; décochée ⇒ selon `directorMode`, `directorStepR2V1` (mode Réalisateur, défaut pour ce pipeline) ou `generateReference2Video` (mode Auto)). Un nouveau builder = une fonction `(seed, width, height)` + une entrée dans `BUILDERS`.
4. Sinon : boucle `jobsSpec` (1 entrée, ou 1/marché sélectionné en image2image) → `tryCloudGeneration` (modes hybride/cloud, images seulement) sinon template local (le template t2v/i2v choisi porte déjà son audio natif, LTX 2.5 comme Minimax H3 — pas de post-traitement audio séparé) → `applyMinimaxTurbo` si le graphe contient une `LoraLoaderModelOnly` (Minimax H3) → POST → `trackJob`.

## Builders de graphes JS (le cœur du projet)

- `makeGraphBuilder()` → `{g, add}` ; ids séquentiels "1"…
- `addKrea2Shared/addKrea2Shot` : branche image Krea 2 Turbo (8 steps, cfg 1, négatif routé par `ConditioningZeroOut` sur le **positif** — le texte négatif n'est jamais encodé, voir LESSONS piège n°16, toute contrainte doit être formulée en positif dans le prompt). C'est la **seule** branche image du projet : utilisée par `text2image`, par les 3 visuels de `buildCampaignFullGraph` (posters/thumbnails/social), et par `buildCharsheetGraph`/`buildLocsheetGraph` (storyboard_v2 et reference2video).
- `addLtx25Shared` : loaders LTX 2.5 (transformer distillé 22B, VAE vidéo + VAE audio dédiés, 2 `CLIPLoader` gemma4 — un pour le conditioning principal, un pour l'enhancer de prompt) + `SamplerEulerAncestral(eta 0)` + `ManualSigmas` 8 steps (`FLF2V_SIGMAS`). Utilisée uniquement par `buildFLF2VGraph` (pipeline `sequence2video`) — `storyboard_v2` ne l'utilise pas : ses cuts vidéo passent par le template `api/ltx25_i2v.json` (2 passes, prompt-enhancer intégré), pas par ce builder JS.
- `addLtx25Enhance(add, sh, prompt, seed, imageRef)` : prompt-enhancer intégré LTX 2.5 (`TextGenerateLTX2Prompt`) — indispensable car le distillé tourne à cfg 1 (voir LESSONS piège n°5). Contrairement au 2.3, il accepte une image en entrée : ancré sur la 1ʳᵉ image de chaque segment FLF2V pour l'empêcher d'inventer une scène sans rapport (piège n°9, même racine que pour les cuts storyboard).
- `addFLF2VChain` : segments first/last-frame (2×`LTXVPreprocess` → 2×`LTXVAddGuide` frame_idx 0/-1 strength 0.7 → `LTXVDualCFGGuider` → `SamplerCustomAdvanced` → `LTXVCropGuides` → `VAEDecodeTiled`), audio natif optionnel par segment (`LTXVEmptyLatentAudio`/`LTXVConcatAVLatent`/`LTXVSeparateAVLatent`/`LTXVAudioVAEDecode`), concat images `ImageBatch` + audio `AudioConcat`. Utilisée uniquement par `buildFLF2VGraph` (`sequence2video`) — sans notion de tenue de plan final (voir plus bas pour l'équivalent `storyboard_v2`).
- `addGrid` : contact-sheet `ImageStitch`, grille carrée adaptative (`cols = ceil(sqrt(n))`, ex. 4→2×2, 8/9→3×3, 16→4×4), lignes remplies à gauche et équilibrées (une ligne trop courte serait étirée par `match_image_size`).
- `applyMinimaxTurbo(graph, turboOn, steps)` : bascule turbo Minimax H3 (t2v/i2v/r2v) — les 3 templates câblent la LoRA turbo en dur (`LoraLoaderModelOnly`, `strength_model 1`) alimentant à la fois `BasicScheduler` et `BasicGuider`, il n'y a pas de nœud bascule côté ComfyUI ; `turboOn:false` retire la LoRA du graphe et remonte les steps à 20 (comportement inchangé, quel que soit `steps`). No-op silencieux sur tout graphe sans `LoraLoaderModelOnly` (Krea 2, LTX 2.5). Le 3ᵉ paramètre `steps` est **optionnel et rétrocompatible** : omis (appel à 2 arguments), le graphe rendu est strictement celui d'avant — LoRA et steps du template intouchés. Fourni et turbo actif : `6` ou `8` conservent la LoRA turbo du template et fixent seulement `BasicScheduler.steps` ; `4` **bascule la LoRA** vers `MINIMAX_FL2V_LORA_4STEP` (`H3/minimax_h3_fl2v_turbo_4step_v1.2_768p_comfyui_bf16.safetensors`), un LoRA distinct entraîné spécifiquement pour 4 steps — la LoRA d'origine casse la colorimétrie à 4 steps (constat toujours valide, voir addendum LESSONS piège n°12), ce nouveau LoRA ne présente pas ce défaut (validé rendu réel). Cette LoRA de secours est spécifique aux checkpoints `fl2v` (t2v/i2v) — incompatible avec le checkpoint `ref2va` de `reference2video` — donc `reference2video` continue d'appeler `applyMinimaxTurbo(graph, turboOn)` à 2 arguments seulement, sans sélecteur de steps dans l'UI (`turboStepsWrap` absent de ses `controls`).
- `applyStyleLora(graph, loraName, anchorClassType)` (`index.html`, portée depuis Canvas sous le nom `addH3StyleLora` de `js/engine.js`) : greffe une LoRA de style au graphe déjà construit — retrouve le nœud dont le `class_type` vaut `anchorClassType`, lit sa source `inputs.model`, insère une nouvelle `LoraLoaderModelOnly` entre cette source et tout nœud qui la référençait (`strength_model 1`). Généralisée sur le `class_type` d'ancrage car les templates diffèrent : `KSampler` pour `krea2_t2i`, `BasicScheduler` pour les 3 templates Minimax H3 (mêmes anchors que ceux dont dépend `applyMinimaxTurbo`, confirmés en lisant les JSON réels des templates). No-op si `loraName` est vide ou si `anchorClassType` est absent du graphe (LTX 2.5 : ni `KSampler` ni `BasicScheduler` pertinent). **Ordre d'appel obligatoire : toujours après `applyMinimaxTurbo`, jamais avant** — `applyMinimaxTurbo` retrouve sa propre `LoraLoaderModelOnly` par `class_type`, une LoRA de style insérée en premier serait retrouvée à sa place (ou l'ordre d'itération des clés déciderait au hasard).
- **Découverte live des LoRA (remplace la curation manuelle)** : `KREA2_LORAS`/`H3_STYLE_LORAS` (listes `[fichier, libellé]` alimentant les sélecteurs de style Krea 2/Minimax H3) ne sont plus des tableaux figés à la main — `fetchLoraOptions()` scanne `GET /object_info/LoraLoaderModelOnly` (endpoint ComfyUI existant, re-scanné en direct à chaque appel) et pousse (`push`, pas réassignation) tout fichier trouvé sous `Krea2/`/`H3/`, à l'exception des 2 LoRA turbo H3 déjà pilotées par le toggle turbo/steps dédié (`H3_TURBO_LORAS`, seule exclusion). Implémentée deux fois **verbatim** : `js/engine.js` (Canvas) et `index.html` (Studio, fichier autonome qui n'importe pas `js/engine.js`) — toute nouvelle LoRA turbo à exclure doit être ajoutée aux deux copies. Les combos litegraph de `js/nodes-simple.js`/`js/nodes-advanced.js` lisent ces tableaux via une **fonction** (`values: () => E.KREA2_LORAS.map(...)`), pas un tableau pré-calculé — litegraph relit `options.values()` à chaque ouverture du menu, donc la liste reste à jour même si le fetch réseau se termine après la construction du nœud ; côté Studio, le `<select>` DOM (`#loraStyleSelect`) n'a pas cette relecture automatique et doit être repeuplé explicitement par `renderLoraSelect()` (appelée au changement de pipeline/modèle et une fois le fetch résolu).
- `mergeGraph(g, other, prefix)` : fusion de graphes API par préfixage des ids — utilisé pour insérer le teaser LTX 2.5 t2v (`api/ltx25_t2v.json`, repris tel quel via `getTemplate`+`buildGraph`) dans `buildCampaignFullGraph`.

### `storyboard_v2` — orchestration multi-jobs côté page (pas un graphe unique)

Contrairement aux autres builders (un seul graphe API POSTé une fois), `storyboard_v2` est une **séquence de jobs ComfyUI indépendants orchestrée en JS** (`generateStoryboardV2` pour le mode Auto, `directorStep1/2/3` pour le mode Réalisateur) : chaque étape attend la précédente via `waitForJobs` (poll `/history`, intervalle 1.5 s) puis récupère l'image/vidéo produite et la ré-uploade comme entrée de l'étape suivante via `reupload` (pattern `/view` → `/upload/image`). Depuis l'évolution **ancrage double** (2026-07-17), le pipeline fige DEUX fiches structurées gemma (personnage ET décor) et produit DEUX planches Krea 2, toutes deux servant d'entrée à chaque keyframe via un template Qwen-Edit **dual** (2 images). Étapes, dans l'ordre réel du code :

1. **Fiche personnage** (`characterSheetFromBrief`) : un appel gemma4 **structuré** (`format:"json"`) qui fige une description dense du personnage principal du brief, en anglais, sous forme d'objet `{"face","hair","outfit","accessories","palette"}` — chaque champ ~10-20 mots, sans mention de caméra/scène/action. `fieldText` aplatit les valeurs (gemma renvoie parfois des objets imbriqués) puis les 5 champs sont concaténés en une seule chaîne `charDesc`, réutilisée telle quelle par toutes les étapes suivantes.
2. **Fiche décor** (`locationSheetFromBrief`) : appel gemma4 symétrique et indépendant, qui fige le lieu principal du brief en objet `{"place","architecture","materials","lighting","palette"}` (sans mention de caméra/personnage/action), concaténé en une seule chaîne `locDesc`.
3. **Charsheet image** (`submitCharsheetJob` → `buildCharsheetGraph`) : Krea 2 Turbo (`addKrea2Shared/addKrea2Shot`, 8 steps cfg 1), 1920×1088, sur fond gris neutre studio — turnaround plein pied 4 poses (face/¾/profil/dos), portrait visage en gros plan, rangée d'expressions (neutre/souriant/surpris/déterminé), gros plans costume, bandeau de nuances couleur. À cfg 1 le négatif de `KSampler` est un `ConditioningZeroOut` du positif — le texte négatif n'est jamais encodé (LESSONS piège n°16) — donc toutes les contraintes (pas de texte/cadres/planche/collage) sont formulées **positivement** dans le prompt via la constante `SHEET_CLEAN`. Sortie `studio/story/charsheet`. C'est l'**ancre d'apparence** (image 1) de chaque keyframe.
4. **Locsheet image** (`submitLocsheetJob` → `buildLocsheetGraph`) : même branche Krea 2 + `SHEET_CLEAN`, fond neutre sombre, plusieurs plans larges du lieu sous des angles différents + rangée de plans moyens de structures clés + gros plans matières/détails, lieu explicitement vidé de toute présence humaine (formulé en positif : « completely empty and deserted »). Sortie `studio/story/locsheet`. C'est l'**ancre d'environnement** (image 2) de chaque keyframe. Les deux planches (3 et 4) sont soumises en parallèle, avant même la fin du découpage en plans.
5. **Liste de plans** (`shotListFromBrief(n)`) : un troisième appel gemma4 (indépendant des deux précédents) qui découpe le brief en exactement N plans `{scene, angle, motion}` — un seul personnage par plan, scène/décor imposés par le brief, uniquement caméra/moment qui varient. Repli statique (`SHOT_ANGLES`/`FALLBACK_MOTIONS`) si gemma échoue ou renvoie un format inattendu (`normShot` normalise aussi les objets imbriqués que gemma renvoie parfois à la place de chaînes).
6. **N keyframes ancrées DUAL** (`submitKeyframeJob`, 1 job Qwen-Edit par case) : le template désigné par le champ manifest **`anchor`** (`api/qwen_edit_dual.json`, Qwen-Image-Edit 2509 + LoRA Lightning 4 steps, cfg 1) reçoit **2 images d'entrée** — `image` = charsheet, `image2` = locsheet (placeholders `{{IMAGE}}`/`{{IMAGE2}}` substitués par `buildGraph`) — et le prompt `keyframePrompt(shot, charDesc)`, qui précise explicitement d'utiliser la 1ʳᵉ image comme guide d'apparence du personnage et la 2ᵉ comme guide d'environnement, sans split-screen/diptyque/collage. Dans le graphe (`workflows/api/qwen_edit_dual.json`), seule l'image 1 (charsheet) alimente le `VAEEncode` qui devient le latent de départ du `KSampler` ; l'image 2 (locsheet) n'alimente que les nœuds `TextEncodeQwenImageEditPlus` (conditioning positif ET négatif) — **elle ne touche jamais le latent**. Ce prompt reste entièrement **positif** (cfg 1 → negative prompt ignoré, voir LESSONS) : une seule instance du personnage, rendu **"photorealistic cinematic film still"** sans cadre/marge/planche/légende. Bascule de modèle d'ancrage = changer uniquement `anchor` dans le manifest (l'ancien template mono-image `api/qwen_edit_i2i.json` reste sur disque, non référencé).
7. **Grille contact-sheet** (`submitGridJob` → `addGrid`) : job "fire-and-forget" (le pipeline ne l'attend pas, il continue vers les cuts) — cols adaptatif `ceil(sqrt(n))`.
8. **1 cut i2v par keyframe** (`submitCutJob`, template `api/ltx25_i2v.json` tel quel) : le prompt du cut ancre l'enhancer LTX sur le contenu réel de la keyframe — `` `${scene}. ${charDesc}. ${locDesc}. Camera motion: ${motion}.` `` (scène du plan + identité personnage + description du décor + mouvement de caméra, voir LESSONS piège n°9) — la taille vidéo est dérivée de la taille réelle de la keyframe (`videoSizeFor`, côté long ≤1280, multiples de 32). Une **tenue du plan final** optionnelle (`holdDur > 0`) ajoute un cut supplémentaire sur la dernière keyframe avec le même ancrage scène+charDesc+locDesc et un mouvement figé ("Locked camera holding…") — implémentée simplement en poussant une case de plus dans `cutKeys`/`motions`, pas par un mécanisme dédié dans un builder JS.
9. **Assemblage** (`submitAnimaticJob` → `buildAnimaticGraph`) : **cuts francs** (pas d'interpolation FLF2V) — chaque cut vidéo est décomposé (`LoadVideo`→`GetVideoComponents`), les images concaténées (`ImageBatch`) et les pistes audio concaténées (`AudioConcat`) si l'audio est activé, puis réassemblées en un seul fichier (`CreateVideo`/`SaveVideo` → `studio/story/animatic`).

**Mode Réalisateur** (contrôle manifest `mode`, bouton `modeAutoBtn`/`modeDirectorBtn`, état `directorMode`/`director`) : mêmes fonctions d'étape que le mode Auto, mais avec une **ÉTAPE 0** de contrôle des deux planches d'ancrage avant tout le reste — `directorStep1` soumet immédiatement les jobs charsheet ET locsheet (pendant que gemma découpe les plans en parallèle) et affiche une carte par planche (`renderAnchorCard`, zone `anchorCardsWrap`) avec statut (Génération…/Prêt/Erreur) et un bouton 🔄 Régénérer (`regenerateAnchor` : reseed `+1` la planche concernée, resoumet, **ré-invalide** la session — `director.validated = false`) ; le bouton **"Valider les planches"** (`directorValidateBtn`) ne s'active que quand les deux planches sont `ready` (`anchorsReady`), et sa validation (`director.validated = true`) est la condition (`updateGateState`) qui révèle la liste de plans éditable et le bouton keyframes — toute régénération d'une planche après validation ré-invalide et re-masque la suite. Ensuite : `directorStep2` (1 carte par keyframe, **régénérable** — `regenerateKeyframe` reseed `+1` — ou **verrouillable** — `toggleLockKeyframe` — avant de continuer ; `directorLaunchBtn` ne s'active que quand toutes les cases sont `ready`), `directorStep3` (grille + cuts + assemblage, identique aux étapes 7-9 du mode Auto via les mêmes `submitGridJob`/`submitCutJob`/`submitAnimaticJob` — `directorStep3` déstructure `charDesc`/`locDesc` du même état `director` que l'étape 0 et les passe à `submitCutJob` exactement comme `generateStoryboardV2`, donc le même ancrage cut protège les deux modes).

**Coquille studio partagée par 2 pipelines (`director.pipeline`, 2026-09-08)** : le shell plein écran (`enterStudio`/`exitStudio`, `#studioNav`, `STUDIO_SECTIONS`) et le cœur générique de revue de planches (`director.charFields/locFields/charVariants/locVariants/charActive/locActive/validated`, `renderSheetMenu`/`regenerateSheet`/`importSheetImage`/`anchorsReady`/`updateValidateButtonState` — l'ÉTAPE 0 ci-dessus) ne sont **pas** spécifiques à `storyboard_v2` : ils opéraient déjà génériquement sur des `kind` `"char"`/`"loc"`. `reference2video` réutilise ce même cœur pour sa propre session Réalisateur (voir section `reference2video` plus bas), avec une 3ᵉ étape différente (Vidéo, pas Storyboard/Montage). Chaque objet `director` porte désormais un tag `pipeline` (`"storyboard_v2"` ou `"reference2video"`, posé par `directorStep1`, `directorStepR2V1` et le chemin de reprise de `restoreProject`) qui pilote deux points de branchement :
- `updateStudioNavForPipeline()` : montre/masque les onglets `#studioNav` — `storyboard`+`montage` pour `storyboard_v2`, `video` (nouvel onglet `#studioVideoR2V`, section minimale : ligne de statut + bouton `#directorR2VLaunchBtn` "Lancer la vidéo") pour `reference2video`. `director` absent (pas de session, ex. juste après un reset) retombe sur la forme `storyboard_v2` par défaut — comportement identique à avant l'introduction du 2ᵉ pipeline.
- `updateGateState()` : branche sur `director?.pipeline === "reference2video"` (et non `=== "storyboard_v2"`, voir LESSONS piège n°18 sur ce choix) — pour r2v, `unlocked` (`anchorsReady() && director.validated`, même condition que `storyboard_v2` utilisait déjà pour débloquer son onglet Storyboard) active/désactive directement `#directorR2VLaunchBtn` et l'onglet Vidéo au lieu de la liste de plans/bouton keyframes et des onglets Storyboard/Montage.

Le sélecteur Auto/Réalisateur (contrôle `mode`) est désormais dans les `controls` des deux pipelines (`PIPELINES_FALLBACK` + `workflows/manifest.json`), mais le **défaut** diffère : `updateModelOptions()` appelle `setDirectorMode(true)` uniquement quand le pipeline nouvellement sélectionné est `reference2video` — `storyboard_v2` garde son défaut Auto (`directorMode = false` au chargement de la page) inchangé.

**Persistance/reprise (LOT C, `saveProject`/`restoreProject`, clé localStorage `studioProject`) reste strictement `storyboard_v2`** : `saveProject()` est gardée par `if (!director || director.pipeline !== "storyboard_v2") return;` — une session Réalisateur `reference2video` n'a rien d'analogue à "reprendre" (2 fiches puis un seul job vidéo, pas de `shots`/`keyframes`/`cutPlan`) ; sans cette garde, `saveProject()` aurait écrit un blob de projet malformé/incomplet que `restoreProject()` ne sait reconstruire que sous la forme `storyboard_v2` (elle force `pipeline: "storyboard_v2"` sur tout ce qu'elle restaure), cassant silencieusement la reprise pour de vraies sessions `storyboard_v2` partageant la même clé `localStorage`.

**Qualification (rendu réel, 2026-07-17)** — run Auto N=8 (cuts 2 s + tenue 2 s, audio ON) : identité personnage cohérente sur les 8 keyframes (image fixe), grille 3×3 (3+3+2) équilibrée, animatic = exactement 9×49 = 441 frames (`ffprobe`, aucune dérive de comptage), audio aac continu 128 kbps sur toute la durée (pas de silence détecté aux coupes). Timings mesurés et projection N=16 : voir `workflows/README.md` et le rapport de qualification LOT 3.

**Risque CRITIQUE identifié (frames extraites en milieu de cut, pas seulement au premier/dernier point)** : les cuts vidéo (étape 6, LTX i2v) dérivent souvent vers un contenu **sans rapport** avec la keyframe/le personnage — sur le run N=8, seuls 3/9 cuts gardent clairement le personnage et le décor, 4/9 dérivent totalement (fontaine, rue, homme agenouillé, champ de blé). Cause probable : le prompt du cut est réduit à `shot.motion` seul (pas de scène/personnage), amplifié à l'aveugle par l'enhancer texte-only du template (`TextGenerateLTX2Prompt`, aucune entrée image) sous cfg 1 — voir LESSONS piège n°9 (détail, preuves, piste de correction). Ce risque touche la fidélité de fond de l'animatic, indépendamment de l'ancrage Qwen-Edit. ## Backend `updater` (`docker/updater/server.py`)

Seule exception au "tout côté client" de la vue d'ensemble : un serveur HTTP Python stdlib (zéro dépendance), `ThreadingHTTPServer` sur `127.0.0.1:8093`, reverse-proxifié par `nginx.conf` sous `location /update/`. Trois routes :

- `GET /status` : compare `git rev-parse HEAD` local à `git ls-remote origin main` distant.
- `POST /apply` : `git fetch` + `git pull --ff-only`, refuse proprement si le working tree n'est pas clean (jamais de force/stash).
- `POST /loras/upload?folder=<Krea2|H3>&filename=<nom>.safetensors` : reçoit le corps de requête comme octets bruts (pas de parseur multipart — l'image `python:3-alpine` en 3.12 n'a plus le module `cgi`, et le frontend XHR le `File` brut avec `folder`/`filename` en query string). Validation : `folder` contre une liste blanche stricte (`{"Krea2", "H3"}`), `filename` assaini (`os.path.basename`, doit rester identique à la valeur brute, aucun `..`, extension `.safetensors` obligatoire), `Content-Length` requis et numérique. Écriture en streaming par blocs de 1 Mo dans `<LORAS_DIR>/<folder>/<filename>.part`, puis `os.rename()` atomique vers le nom final **seulement** si le compte d'octets écrits correspond exactement à `Content-Length` (sinon le `.part` est supprimé et la requête rejetée) — nécessaire car `/object_info`/`/models/loras` de ComfyUI re-scannent le dossier à chaque appel : un fichier partiellement écrit visible en cours d'upload pourrait être sélectionné et utilisé cassé.

Chaîne de détection du chemin LoRA (`LORAS_DIR`/`COMFY_LORAS_DIR`) : `docker-compose.yml` monte `${COMFY_LORAS_DIR:-./comfyui/basedir/models/loras}:/loras:rw` sur le service `updater` (env `LORAS_DIR=/loras`, interpolation `.env` native de docker-compose, pas de plugin) ; `install.sh` écrit ce `.env` (`COMFY_LORAS_DIR=$COMFY_MODELS_DIR/loras`) après sa détection déjà existante du vrai chemin hôte d'un ComfyUI externe réutilisé, puis force `docker compose up -d --build --force-recreate updater` pour que le mount change prenne effet. `.env` est dans `.gitignore` (spécifique à la machine, généré). `nginx.conf` : `client_max_body_size 10g;` sur `location /update/` (des LoRA de plusieurs Go dépasseraient sinon la limite par défaut de 1 Mo).

Côté UI (`index.html`, carte "LoRAs" du panneau Model Management) : inventaire live via `GET /comfy/models/loras` (même schéma que `diffusion_models`/`checkpoints` déjà affichés là), formulaire d'ajout câblé en `XMLHttpRequest` — pas `fetch` — pour disposer de la progression réelle (`xhr.upload.onprogress`).

## Ajouter un modèle / workflow (outillé)

`tools/onboard.py <workflow_ui.json> --id <id> --label "<label>" --pipeline <p> --model "<nom>" [--fps N] [--enrich builtin]` fait toute la chaîne : rafraîchit `object_info`, convertit le format UI en API (`convert.py`), **injecte les placeholders** (`{{PROMPT}}`/`{{NEGATIVE_PROMPT}}` sur les CLIPTextEncode positif/négatif — ou l'input `prompt` du `TextGenerateLTX2Prompt` s'il est sur le chemin —, `{{SEED}}`, `{{WIDTH}}/{{HEIGHT}}/{{BATCH}}` des `Empty*Latent*`, `{{FRAMES}}` des latents vidéo, `{{IMAGE}}` des `LoadImage`), vérifie les `.safetensors` sur disque, écrit `workflows/api/<id>.json`, ajoute l'entrée manifest, puis lance `validate.py --reduce`. Le workflow source vient soit de `workflows/*.json`, soit d'un template officiel du conteneur (`docker exec comfyui-nvidia cat …/templates/<x>.json`).

`tools/validate.py <api.json> [--reduce] [--frames 0,12,24] [--audio] [--image <fichier>]` : vérif structurelle (nœuds dans `object_info`, liens intègres, modèles sur disque) → substitution des placeholders par des valeurs de test → soumission → poll → extraction frames/mp3 pour inspection. **Toujours regarder le contenu produit**, pas seulement le statut (cf. `docs/TESTING.md`).

**Nouveau pipeline** (jeu de contrôles UI inédit) : ajouter une entrée à `pipelines[]` du manifest (`controls`, `scenario?`, `fps?`) — aucun JS à toucher si les contrôles existent déjà. **Nouveau builder JS** : une fonction `(seed, width, height)` + une entrée dans le registre `BUILDERS` + `{file:null, builder:"<nom>"}` au manifest.

### Monter un modèle en version supérieure
Ré-onboarder le template officiel de la nouvelle version sous un id suffixé (`_v2`) au lieu d'écraser : `onboard.py … --id <base>_v2`. Les deux apparaissent alors dans le menu Modèle → rendu **A/B côte à côte** dans la galerie (même brief/seed). Une fois la nouvelle version validée, retirer/renommer l'ancienne entrée manifest (le fichier api reste, réactivable en 1 ligne). Piège récurrent : un checkpoint peut diverger du nom donné par le template officiel sans que rien ne le signale avant le rendu (cf. Minimax H3 : `*_pruned_w4a8_mixed.safetensors` réel vs `*_pruned_int8_convrot.safetensors` du template, ou les deux checkpoints t2v/i2v vs r2v — `fl2va` vs `ref2va`, à ne pas confondre — LESSONS piège n°14) — `onboard.py` détecte les fichiers manquants, `validate.py` attrape au rendu les incompatibilités de dimensions/checkpoints que la vérif structurelle laisse passer. Ne jamais conclure d'un statut de job "success" : toujours inspecter les pixels/l'audio produits (LESSONS piège n°14, découvert précisément par un job "réussi" mais visuellement faux).
